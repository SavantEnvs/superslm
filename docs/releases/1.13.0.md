# SuperSLM 1.13.0

Not yet released. TODO-BOX: the release date, filled when the tag is made.

SuperSLM 1.13.0 brings 1.12.0's paged K/V memory to the GPU backend. A GPU page pool holds the K/V of
budgeted sequences and prefixes in pages. A budgeted sequence reserves only the pages its budget
needs, sequences that adopt a frozen prompt prefix map the prefix's full pages instead of copying
them, and a budgeted sequence's save, the new `SLM6` blob, holds its live rows, so its size follows
its live length. It also folds in the fixes planned for a 1.12.1: a no-budget CPU save now writes a
large block with streaming stores, aimed at 1.12.0's save slowdown (the bytes are unchanged, and its
speed on the release machine is not yet read), and two GPU defects that shipped in earlier releases
are fixed (see *Fixes*).

GPU sequences made by `sslm_gpu_seq_create` keep their own whole-cap buffer and keep saving `SLM5`,
which 1.12.0 still reads. They now address K/V through a page table with one page, which by
construction is the old flat layout. Their outputs are meant to be byte-identical to 1.12.0's. On
the NVIDIA GeForce RTX 2080 SUPER, `superslm_tests` with its GPU cells and the GPU fault suites pass
on this branch, while the cross-vendor battery reads red for reasons that predate this release;
nothing in this release is verified on the AMD Radeon RX 7900 XTX (see *Verification*). The memory
savings come only from the new pooled verbs. Two GPU behaviours change for every host (see
*Compatibility*): a second decode of the same sequence handle, raced from another thread, returns
`SSLM_BUSY` where it was undefined, and a call that would reset the process's GPU command list
while earlier work is still unobserved returns `SSLM_BUSY` where it was undefined. The shipped shaders changed, so deploy the whole 1.13.0 shader
set. The CPU C ABI is unchanged (51 verbs, no new status), and no model artifact needs reconversion.

## What changed

- **GPU page pools.** `sslm_gpu_kv_pool_create(ctx, model, page_count, &pool)` creates one device
  buffer of `page_count` pages, zero-filled before it returns, with a host mirror of the same size.
  A GPU page is `B` positions, where `B` is the artifact's `kv_block_size` when it divides the
  context cap and the cap otherwise: 16 for converted artifacts at cap 4,096. That is not the CPU's
  page (64 positions at Qwen2.5-0.5B, cap 4,096), so the two backends' page counts differ for the
  same cohort. A page of Qwen2.5-0.5B is 96 KiB (24 layers × K and V × 2 K/V heads × 16 positions ×
  64 bytes) and of Qwen2.5-1.5B 224 KiB, from the page rule. `sslm_gpu_kv_pool_destroy` destroys an
  empty pool and refuses with `SSLM_MODEL_HAS_LIVE_SEQUENCES` while anything drawn from it lives.
  `sslm_gpu_kv_pool_stats` reports the pool's page count, free and shared pages and its `B`.
- **Budgeted GPU sequences.** `sslm_gpu_seq_create_budgeted(ctx, model, pool, budget, &seq)` takes a
  budget, `1 ≤ budget ≤ cap`, and reserves `R(budget) = min(ceil(budget / B) + 1, ceil(cap / B))`
  pages at create, the CPU's rule, or returns `SSLM_GPU_KV_POOL_EXHAUSTED` with nothing drawn. Decode
  and prefill then take pages only from that reservation. A write at or past the limit,
  `min(origin + budget, cap)`, below the cap returns `SSLM_GPU_KV_BUDGET_EXCEEDED` with no row
  written; at the cap the existing cap behaviour applies. Every other GPU verb (decode, the batch,
  prefill, the finish, reset, release, schema binding) takes a pooled sequence as it takes a
  dedicated one, and its reset and release touch only its own pages.
- **Shared GPU prefixes.** `sslm_gpu_prefix_begin`, `sslm_gpu_prefix_set_schema`,
  `sslm_gpu_prefix_prefill`, `sslm_gpu_prefix_freeze` and `sslm_gpu_prefix_release` build budgeted
  prefixes in a pool, base-only. `sslm_gpu_prefix_begin_from` builds a prefix on a frozen parent,
  sharing its full pages and copying its partial last page, so prefixes nest (a world, then a persona
  on the world). `sslm_gpu_seq_adopt_prefix` adopts a frozen prefix onto a pooled sequence the same
  way, with the CPU adopt's field and schema rules; every check runs before any state change. A
  shared page is freed when the prefix and every holder that maps it have let go of it.
- **Save and restore, `SLM6`.** A pooled sequence's `sslm_gpu_seq_save` writes `SLM6`: the `SLM5`
  header and tail, then its mode, budget and origin, its residual, and its rows from position 0 to
  its live length (an adopted prefix's span included), so its size follows its live length.
  `sslm_gpu_seq_restore_into_pool` restores an `SLM6` blob into a fresh pooled sequence with its
  budget and origin, and takes an optional live prefix handle: when the handle matches, the restored
  sequence maps the prefix's pages again, and otherwise it restores privately and still succeeds.
  Dedicated sequences keep writing `SLM5`, and `sslm_gpu_seq_restore` keeps reading `SLM5` and `SLM4`.
  Each restore verb refuses the other's blobs with `SSLM_GPU_HOLDER_MODE_MISMATCH`, changing
  nothing. In the software-GPU runs, a GPU `SLM6` blob's K/V section equals the CPU `SSB6` blob's of
  the same state byte for byte; the two remain separate formats, and neither backend restores the
  other's blobs.
- **Statuses.** Six `SslmGpuStatus` values are appended, ordinals 24 to 29:
  `SSLM_GPU_KV_BUDGET_EXCEEDED`, `SSLM_GPU_KV_POOL_EXHAUSTED`, `SSLM_GPU_KV_POOL_TOO_LARGE` (a pool
  above 2^32 bytes, the reach of the shaders' 32-bit offsets: 43,690 pages at Qwen2.5-0.5B and 18,724
  at Qwen2.5-1.5B, from the page rule), `SSLM_GPU_HOLDER_MODE_MISMATCH`, `SSLM_GPU_PREFIX_REJECTED`
  and `SSLM_GPU_PREFIX_SCHEMA_MISMATCH`. No existing ordinal moves.
- **Work in flight, stated.** `gpu_1p0.h` now states two promises. Safety: the library never resets
  a device's command allocator while work submitted on it has not been observed complete, whatever
  path reached the reset. A clean status: a guarded verb that would do so returns `SSLM_BUSY` and
  changes nothing, or `SSLM_DEVICE_LOST` once a submission is stranded, never a Busy a retrying host
  would spin on. The header lists, for every verb, which device it resets, submits or waits on, and
  the order of each verb's refusals. Both hold for a host that serializes every call that submits on
  a device, as before; the list of those calls is now complete (see *Compatibility*).

`gpu_1p0.h` adds 12 verbs and 2 handle types (`SslmGpuKvPoolHandle`, `SslmGpuPrefixHandle`), plus
two test-only verbs (`sslm_gpu_test_only_peek_pool_mirror_bytes`,
`sslm_gpu_test_only_wait_in_flight`) that a host does not call. `docs/api.md` (*Paged KV memory on
the GPU*) is the summary, and the header is the contract.

## Fixes

- **A barrier race in the shipped shaders.** Four steps run more than once in one dispatch: the
  residual candidate of the attention and MLP residual sites, the bias reconcile and the funnel
  maximum. Thread 0 reset a shared flag or maximum slot for the second run without a barrier after
  the first run's reads, so another thread could read the reset value and reach a barrier the others
  did not. The fix adds the barrier. It was found by running the GPU path on a software Vulkan device
  (lavapipe), where the race fired on every run: 16 GPU-against-CPU mismatches in `superslm_tests`
  went away with it. In earlier releases' certification runs on the two certified GPUs, GPU outputs
  were byte-identical to the CPU's, so the race had not shown there. No output is meant to change.
  On the RTX 2080 SUPER, `superslm_tests` with its GPU cells passes with the fix (see
  *Verification*); the AMD card has not run it.
- **No-budget CPU save speed.** 1.12.0's no-budget `sslm_seq_save` copied the block one page run at
  a time, each copy too small for the C runtime to use non-temporal stores, so every destination
  line was first read into the cache, and the save took 1.14 to 2.00 times as long as 1.11.0's. A
  block of 16 MiB or more (24 MiB at Qwen2.5-0.5B, cap 4,096; 448 MiB at Qwen2.5-1.5B, cap 32,768)
  is now written with streaming stores on x64; a smaller block, and every non-x64 target, keeps
  1.12.0's copy. The bytes are unchanged: blobs equal 1.11.0's and 1.12.0's at 9 lengths, and the
  streaming path is checked against the pinned 1.11.0 blobs at every destination offset from 0 to
  63 (cell 9.3s). TODO-BOX: the release machine's lifecycle save readings against 1.11.0 (see
  *Speed*).
- **Two decodes racing on one GPU sequence.** Two threads decoding the same sequence handle at once
  is not a supported use, but in 1.12.0 and earlier it was undefined: both calls could pass the
  handle's checks and record on the one command list together, which corrupted the heap under the
  D3D12 debug layer and, without it, returned `SSLM_OK` to one call and `SSLM_DEVICE_LOST` to the
  other and left the sequence unreleasable. Now one call runs and the other returns `SSLM_BUSY`
  having changed nothing (a batch slot reads `SSLM_BUSY`). Other verbs raced on one handle remain
  the caller's to serialize.

Found and fixed during development, never released: a host allocation failure while publishing a
GPU call's timing was swallowed into `SSLM_OK` by two publishes the pool work added; it now returns
`SSLM_GPU_ALLOCATION_FAILED`, as every other host allocation failure does. A pooled sequence's page
table was left in a shader-read state between uploads, so later uploads copied into it from a
state other than the one they declared; it now returns to the common state between uploads.
Releasing a prefix after its sequence's release returned an error left a dangling handle; it now
completes unless the release returned `SSLM_BUSY`. The other changes since 1.12.0 are to comments,
test cells, test tools and build scripts, the coverage job's build list among them.

## Memory, graded by admission

The figures are graded by what a pool admits, never by the library's page counts, on the 1.12.0
example cohort, an assumption, not a measured workload: a 1,000-token world prefix, 10 persona
prefixes of 200 tokens built on it with `sslm_gpu_prefix_begin_from`, the world handle released, and
50 budgeted sequences of 512 tokens each (5 per persona), each run to its budget. At Qwen2.5-0.5B
with cap 4,096 a GPU page is 96 KiB (16 positions).

- A pool of **1,842 pages** (172.7 MiB) admits the whole cohort, and a pool of **1,841 pages** refuses
  exactly one create, the 50th, with `SSLM_GPU_KV_POOL_EXHAUSTED` (cell 10.5). Fifty 1.12.0-style
  dedicated sequences at cap 4,096 hold 24 MiB of K/V each, 1,200 MiB in all (arithmetic from the
  dedicated buffer's size, which the cell reads from a dedicated sequence's own save; the GPU has no
  block pool to refuse an eighth sequence, so there is no admission contrast).
- After every sequence is saved mid-budget and at its limit, the world and personas rebuilt in a
  fresh pool and the world released, the 50 sequences restored **with** their persona handles fit
  in **1,842 pages**, and 1,841 refuses exactly the 50th, for both saves (cell 10.7).
- Restored **without** handles, the same blobs need **5,592 pages** (5,591 refuses the 50th); after
  each sequence resets and re-adopts its persona the pool admits **113** more budget-512 sequences
  (cell 10.7).
- Every sequence's tokens equal the CPU twin's, which equal a no-sharing 1.11.0 run (cell 10.3).

All four are confirmed on the real Qwen2.5-0.5B artifact on the RTX 2080 SUPER with the D3D12 debug
layer on, at commit `845918e` (see *Verification* for what changed after it). TODO-BOX: the check
counts of the three cells' real-artifact legs. They are not run on the AMD card. Each cell also has a
fixture leg, on the small synthetic model of the paged-KV suites, which passed on the software GPU
(10.3: 280 checks, 10.5: 217, 10.7: 793; 0 failures). The figures hold for this artifact's page size
only. Another model or cap has another page size and its own figures.

## Speed

- **Paged GPU decode against the legacy one-page view.** The claim is a bar: on the release
  machine's NVIDIA GeForce RTX 2080 SUPER, single-sequence GPU decode of a cohort member through its
  page table is no more than 5% slower than a dedicated sequence through the one-page view of the
  same build, at Qwen2.5-0.5B, cap 4,096, to width 1,712. It passes. The timing harness decodes both
  arms in one process and one context: the paged arm is the first sequence of persona 0 in the
  cohort above, in a pool of exactly 1,842 pages, decoding from 1,200 tokens to its limit, 1,712;
  the legacy arm is a dedicated sequence at cap 4,096 prefilled with the same 1,200 tokens. Each
  timed call is one whole token through the one-call decode (`SslmGpuSeqDecodeStepForG5Bridge`,
  which waits for the token), timed alone, with the two arms alternating in an order drawn at random
  for each pair, and both arms' tokens must be equal at every pair. A run is five fresh
  constructions of 508 timed pairs each. Per pair the slowdown is one minus the legacy time over the
  paged time. Before its reading counted, the harness was shown to reject a paged arm slowed on
  purpose by 17.65% of each call.

  The pooled reading, n = 2,540 pairs, debug layer off: a median slowdown of **−1.21%**, with a
  distribution-free sign interval of −1.29% to −1.11%, so the effect is resolved and the paged arm
  read faster than the legacy arm in this measurement, by about 1.2%. Each of the five constructions
  passed the bar alone. The run reported 31.63 tok/s paged and 31.29 tok/s legacy. This release
  claims the bar, not a speed-up: the reading is one card, one model, one width range and one run.
  The legacy arm is the one-page view of 1.13.0, not 1.12.0's dedicated path; no measurement ties
  1.13.0's GPU decode speed to 1.12.0's, for dedicated or pooled sequences. Decode on the AMD Radeon
  RX 7900 XTX, at Qwen2.5-1.5B, above width 1,712, at another cap, in a batch, and under the debug
  layer is not measured. TODO-BOX: the 2080 SUPER's driver version and the commissioning date, from
  the run's identity record. TODO-BOX: the AMD leg of the decode timing, run on its own machine, if
  this release is to state one.
- **No-budget CPU save against 1.11.0.** TODO-BOX: the lifecycle save cell on the release machine,
  1.13.0 against 1.11.0 at Qwen2.5-0.5B (cap 4,096) and Qwen2.5-1.5B (cap 32,768), live lengths 16,
  1,000 and the cap, in 1.12.0's register (medians, spreads, captures, readings not resolved changes).
  Until it is read, this release states no save speed. In development, a benchmark of the copy
  pattern alone on a cloud Linux machine (not the release machine, and not the library's save call)
  read 1.70 times 1.11.0's time for 1.12.0's copy and 1.08 times for the streaming copy, at
  Qwen2.5-1.5B's full-cap block.
- **Nothing else is claimed.** The CPU decode, reset, adopt and lifecycle claims of 1.12.0 are
  unchanged and were not re-measured (the CPU paths they cover did not change).

## Compatibility and required action

These apply to every host, including one that calls no new verb:

- **Deploy the whole 1.13.0 shader set** with the 1.13.0 library. Every K/V-addressing shader reads
  the page table, and the barrier fix touches the residual sites; the shaders and the library must
  come from the same release.
- **Two decodes raced on one sequence handle**: one runs and the other returns `SSLM_BUSY`, changing
  nothing. It was undefined.
- **A second singleton-reaching call while earlier work is unobserved** (for example, a decode of
  sequence A, then a decode of sequence B before `sslm_gpu_ready` has reported A complete) returns
  `SSLM_BUSY`, changing nothing. It was undefined: it reset the command allocator the earlier work
  was recorded on. Finish each submission (`sslm_gpu_ready`) before the next, or decode several
  sequences in one `sslm_decode_step_batch_gpu` call.
- **A stranded submission** (one whose completion cannot be confirmed) makes every later guarded verb
  that reaches the process's submission device return `SSLM_DEVICE_LOST`, until the process
  restarts. 1.12.0 already documented a stranded submission as terminal; the status is now the same
  from every such verb.
- **The serialization rule is complete.** Every call that resets or submits on a device, and every
  blocking `sslm_gpu_ready`, must be externally serialized against every other such call on that
  device. The header named three calls (the two decodes and the blocking `sslm_gpu_ready`); it now
  lists every one, among them `sslm_gpu_model_map`, `sslm_gpu_adapter_map`, `sslm_gpu_seq_create`,
  `sslm_gpu_seq_restore`, the prefill and finish bridges, and the new pool, prefix, adopt and restore
  verbs. A host that already serializes every GPU call needs no change. Non-blocking
  `sslm_gpu_ready` may still run beside a submitter.
- **The order of two refusals is now documented.** `SslmGpuSeqPrefillSchemaContentForG5Bridge` on a
  Submitted sequence returns `SSLM_BUSY` before it checks the first token's reachability
  (`SSLM_SEQUENCE_REJECTED`). That order is unchanged since 1.6.0; the header now states it, with the
  order of every guarded verb's refusals.
- **`SslmGpuStatus`** gains ordinals 24 to 29 (above). Only pooled sequences, prefixes and the pool
  verbs return them, except `SSLM_GPU_HOLDER_MODE_MISMATCH`, which `sslm_gpu_seq_restore` returns for
  an `SLM6` blob. A host that switches over the enum should add them.
- **No-budget CPU saves** are faster on x64 for blocks of 16 MiB or more (above), with the same bytes.
- **No existing GPU declaration, struct layout or ordinal changes**; the additions are new
  declarations and appended enumerators. The CPU C ABI does not change.

A host that adopts GPU pools should know:

- An `SLM6` blob cannot be read by 1.12.0 or earlier: their `sslm_gpu_seq_restore` refuses it on its
  magic with `SSLM_SEQUENCE_KV_BUFFER_MISMATCH` and creates no sequence (cell 9.8: a binary built
  from the 1.12.0 tree, on the release machine, at commit `845918e`). TODO-BOX: the cell's check
  count.
- Pass an `SLM6` blob to `sslm_gpu_seq_restore_into_pool`, not `sslm_gpu_seq_restore`. Pass each
  restore its live prefix handle: without it a restored sequence holds its prefix span privately
  until it resets or re-adopts (the 5,592 pages above, against 1,842).
- The pool, prefix, adopt and restore-into-pool verbs that submit GPU work return `SSLM_BUSY` while
  any sequence in the process is Submitted, and a guarded verb called on a dedicated sequence
  returns `SSLM_BUSY` while a pooled one is Submitted. A host that mixes pooled and dedicated
  sequences should finish each submission before the next call, as above.
- Size admissions from `sslm_gpu_kv_pool_stats`' free pages, not from handle counts: a shared page
  stays counted until every holder that maps it lets go.
- An adopt of a prefix from another pool, or onto a dedicated sequence, is refused
  (`SSLM_GPU_PREFIX_REJECTED`, `SSLM_GPU_HOLDER_MODE_MISMATCH`).

## Not in this release

- **The AMD Radeon RX 7900 XTX.** The paged GPU surface, and the fixes in this release, are run and
  measured on the NVIDIA card only (see *Verification*).
- **Memory savings for dedicated GPU sequences.** `sslm_gpu_seq_create` keeps one whole-cap buffer
  per sequence, and its `SLM5` save is the whole buffer.
- **A larger GPU page.** The GPU page stays `kv_block_size`, 16 positions for converted artifacts. A
  larger page was the fallback had paged decode missed its bar; it did not.
- **A removed cap, automatic prefix matching, adapter-shaped prefixes and batched shared-prefix
  attention**, as in 1.12.0.
- **Cross-backend blobs.** A GPU blob does not restore on the CPU, nor a CPU blob on the GPU.
