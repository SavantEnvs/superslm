# SuperSLM 1.12.0

Not yet released. TODO-BOX: the release date, filled when the tag is made.

SuperSLM 1.12.0 stores the CPU backend's K/V memory in pages. A sequence can declare a budget, the
positions it will write itself, and reserve only the pages that budget needs instead of a whole
context-length block. Sequences that adopt a shared prompt prefix can share the prefix's pages
instead of copying them, and a budget sequence's save blob holds only the rows it has written.

Output does not change. Tokens, K/V values and the axis digest are bit-identical to 1.11.0 on every
path. A host that calls only the 1.11.0 verbs keeps 1.11.0's behaviour, admission counts and save
blobs, apart from the few changes listed under *Compatibility*. The memory savings come only from
the new budget-mode verbs. The GPU API is unchanged, and no model artifact needs reconversion.

## What changed

- **Pages.** A KV pool is now a pool of pages of `B` positions (`sslm_kv_page_positions`). `B`
  follows from the model's head dimension, context cap and K/V element width, and the artifact's
  stored block size does not select it: 64 for Qwen2.5-0.5B at cap 4,096 and for Qwen2.5-1.5B at
  cap 32,768, the two sizes measured below. `docs/api.md` states the rule. A sequence or prefix
  reaches its K/V through a page table. The old block pool (`sslm_kv_pool_create`) is the same
  number of bytes at a cap `B` divides, cut into `block_count · ceil(cap / B)` pages.
- **Budget-mode sequences and prefixes.** `sslm_seq_create_budgeted` and
  `sslm_prefix_begin_budgeted` take a budget, `1 ≤ budget ≤ cap`, and reserve
  `R(budget) = min(ceil(budget / B) + 1, ceil(cap / B))` pages up front (`sslm_kv_pages_for_budget`).
  Prefill and decode then take pages only from that reservation, so they never fail for lack of pool
  pages below the holder's limit, `min(origin + budget, cap)`. A write past the limit returns the new
  status `SSLM_KV_BUDGET_EXCEEDED` (ordinal 29), with no row written. At the cap the existing
  `SSLM_CONTEXT_CAP_EXCEEDED` fires instead.
- **Shared prefixes.** A budget sequence that adopts a frozen prefix maps the prefix's full pages
  and copies at most one page. `sslm_prefix_begin_from` builds a budget-mode prefix on top of a frozen
  parent the same way, so prefixes can nest (a world, then a persona on the world). A shared page is
  freed when the prefix and every holder that maps it have let go of it. Sequences made by
  `sslm_seq_create` still copy, as before. Sharing, residency by budget and a cheap high cap hold at
  a cap of more than one page; at a cap that fits in one page a holder is a single page, so adopt
  copies it and a budget reserves all of it.
- **Page pools and diagnostics.** `sslm_kv_page_pool_create` sizes a pool in pages
  (`sslm_kv_page_size`, `sslm_kv_page_pool_overhead_size`). `sslm_kv_pool_stats` reports a pool's
  free and shared pages, and `sslm_seq_kv_stats` a sequence's mode, origin, budget, limit and pages.
- **Contiguous pool option (CPU).** `sslm_kv_pool_contiguous_size` and
  `sslm_kv_pool_create_contiguous` build a pool whose page is the whole context cap, one page per
  block: 1.11.0's contiguous layout, through the same page module. Every verb works on it. A holder
  in it takes one page, so adopt and `sslm_prefix_begin_from` copy and share no page, and saves are
  the same in every pool kind, so a blob restores across pool kinds. It gives up what a page pool
  gives a budget holder, which is sharing a prefix's pages and reserving by budget. It is the
  reference that decode speed is measured against (see *Speed*).
- **Save and restore.** A budget sequence saves a new format, `SSB6`: the `SSB5` header plus its mode,
  budget and origin, then only the rows it has written, so its size follows its live length. A
  no-budget sequence keeps saving `SSB5`, byte-equal to 1.11.0's blob, so 1.9.0 to 1.11.0 still read
  every save a 1.11.0-style host makes. Restore keeps a budget sequence's budget, origin and limit.
  `sslm_seq_restore_shared` takes a live prefix handle and re-shares its pages when the prefix's
  bytes match the blob's exactly; without a matching handle it restores privately and still
  succeeds.
- **Softmax fast path.** On the AVX2 and AVX-512 tiers, `SoftmaxRowQ15`'s fast path admits rows up
  to width 32,767 (it was 2^14). Every probability and the returned bool stay bit-identical to the
  1.9.0 body. No speed figure is claimed for it.

`docs/api.md` (*Paged KV memory*) is the full contract: every verb, the `SSB6` layout, the restore
rules, the thread rules and the limits.

## Memory, proved by admission

The memory figures are graded by what a pool admits, never by the library's own page counts. The
example cohort is an assumption, not a measured workload: a 1,000-token world prefix, 10 persona
prefixes of 200 tokens built on it with `sslm_prefix_begin_from`, the world handle then released, and
50 budget sequences of 512 tokens each (5 per persona), each run to its budget. At Qwen2.5-0.5B with
cap 4,096 a page is 384 KiB (64 positions), and a 1.11.0 block is 64 pages (24 MiB).

- A page pool of **505 pages** admits the whole cohort, and a pool of **504 pages** refuses exactly
  one create, the 50th sequence, with `SSLM_KV_POOL_EXHAUSTED`. 505 pages is 189.4 MiB. 1.11.0 holds
  the same cohort in 60 whole blocks, 1,440 MiB. The admission and the refusal are confirmed on the
  release machine (cell 10.4, real Qwen2.5-0.5B artifact).
- A pool of 1.11.0-style blocks (`sslm_kv_pool_create`, unchanged in 1.12.0) in the same 189.4 MiB
  admits **7 sequences** and refuses the 8th, because an eighth block needs 192 MiB. Cell 10.4 runs
  this contrast leg on the 1.12.0 build with the 1.11.0 verb; it is not a run of the 1.11.0 binary.
- After every sequence is saved mid-budget and at its limit, the world and personas rebuilt in a
  fresh pool and the world released, the 50 sequences restored **with** their persona handles fit in
  **505 pages**, and 504 refuses exactly the 50th, for both saves; confirmed on the release machine
  (cell 10.6, real Qwen2.5-0.5B artifact).
- Restored **without** handles, the same blobs need **1,405 pages** (1,404 refuses the 50th), until
  each sequence resets and re-adopts its persona; after that the pool admits **100** more budget-512
  sequences, for both saves; confirmed on the release machine (cell 10.8, real Qwen2.5-0.5B artifact).

These numbers hold in budget mode only, and for this artifact's page size. Another model or cap has
another page size and its own figures. They are confirmed on the real artifact on the release machine.

## Speed

This release makes speed claims for Windows x64, CPU only, at the ordinary background load of the
release machine: an AMD Ryzen 9 3950X (16 cores, 32 logical processors) with AVX2 and without
AVX-512, running Windows 10.0.19045, where the dispatched kernel tier is AVX2. A process watch ran
beside every timing row and listed no process other than the row's own, and the shared-prefix run
read 2% and 3% CPU load before and after. Decode speed is claimed for single-conversation
generation only: one sequence, decoding one token at a time. Nothing is claimed under load, on the
GPU, or for batched decode.

- **Decode, one conversation.** Attention reads K/V one page run at a time. Single-conversation
  decode is no more than 5% slower than the contiguous cache at both targets, to the 0.5B cap of
  4,096 and to width 18,682 at 1.5B, with 7.9b reported (below). The contiguous
  cache is the contiguous pool option of the same build. The comparison is not against 1.11.0, and
  no measurement ties the option to an older layout. Cell 7.9 restores one saved sequence into each
  of two arms on one artifact: the paged arm, in a page pool at the model's page size with its pages
  in scattered order, and the contiguous arm, in a contiguous-option pool. It decodes the same
  tokens in both, alternating one token per arm in an order drawn at random for each pair, and
  times each token alone. A process of 104 pairs gives a median slowdown, paged time over
  contiguous time minus one. A row is five processes on one boot, and it passes when the largest of
  its five process medians is at most 5.0%. The scattered order is no more step-regular than a
  random one; it is not claimed to be a worst case.

  All six rows pass. Each row's figures, in percent slower than the contiguous cache:

  | Model, cap | Restored at | Timed widths | Largest process median | SD of the five medians | Mean of the five, ± 95% half-width |
  |---|---:|---|---:|---:|---|
  | Qwen2.5-0.5B, 4,096 | 1,200 | 1,204 to 1,307 | +1.001 | 0.067 | 0.941 ± 0.083 |
  | Qwen2.5-0.5B, 4,096 | 2,044 | 2,048 to 2,151 | +1.706 | 0.098 | 1.629 ± 0.122 |
  | Qwen2.5-0.5B, 4,096 | 3,988 | 3,992 to 4,095 | +2.682 | 0.089 | 2.582 ± 0.110 |
  | Qwen2.5-1.5B, 32,768 | 8,188 | 8,192 to 8,295 | +1.310 | 0.178 | not stated |
  | Qwen2.5-1.5B, 32,768 | 15,872 | 15,876 to 15,979 | +3.349 | 0.520 | not stated |
  | Qwen2.5-1.5B, 32,768 | 18,678 | 18,682 to 18,785 | +3.861 | 0.439 | not stated |

  At 0.5B the half-width is the resolution of the mean of the five process medians. The largest
  median, which the rule grades, has no resolution of its own. The 1.5B figures are not resolved
  finer than about one point. The same comparison run with two identical contiguous-option arms (an
  A/A run, which should read zero) read +0.05% at the 0.5B row restored at 3,988, and +1.16% and
  +1.13% at the 1.5B rows restored at 15,872 and 18,678, in this measuring session. So 1.5B figures
  carry a session-dependent zero-point offset of about one point. The 1.5B row restored at 8,188 has
  no A/A run of its own, and the offset statement covers it by extension from the other two,
  unmeasured at that width. This release states no 1.5B figure as a paged overhead finer than that
  offset, no figure corrected for the A/A reading, no margin under the 5% bar at 1.5B as
  established, and no ordering of or trend among the 1.5B rows. Decode at widths beyond the table
  (at 1.5B, above 18,785) and at Qwen2.5-0.5B with a cap above 4,096 is not measured.
- **Decode over a shared prefix, reported.** Cell 7.9b times a budget sequence that adopted a
  persona prefix against a sequence holding the same prompt in a contiguous-option pool, on
  Qwen2.5-0.5B at cap 4,096: 508 pairs over widths 1,204 to 1,712, the order drawn at random for
  each pair. The median slowdown is +1.063%, with a sign interval of +0.990% to +1.130% (half-width
  0.070 points), against the same 5% bar. It is reported and is not part of the claim above.
- **Batched decode has no speed claim.** `sslm_decode_step` over several sequences works and stays
  bit-identical: cell 8.1 decodes a no-budget sequence and a budget sequence that share a prefix in
  the same `sslm_decode_step` calls, 40 tokens across page boundaries, and requires each to equal its
  solo no-budget twin in tokens and save blob. It is green in the cloud. On the release machine it
  is one of the 70 cells of the paged-KV suite `superslm_pkv_c5`, which ran green (156 checks in

- **Reset and adopt: cost does not grow with the context cap, except that at head_dim ≤ 64 a cap
  above 4,096 doubles the page and its one-page tail copy (0.5B: 384 KiB at caps up to 4,096, 768

## Compatibility and required action

None for a host that calls only the 1.11.0 verbs, except these changes, which apply to every host:

- **`sslm_seq_state_size` is 20 bytes larger.** Its fixed part is 180 bytes, against 160 in 1.11.0,
  so it stays an upper bound for `SSB6` blobs. A host that sizes save buffers with it needs no change.
- **`sslm_kv_pool_create`** refuses a `block_count` whose page total exceeds `UINT32_MAX` with
  `SSLM_INVALID_ARGUMENT`. At cap 32,768 that is 8,388,608 blocks or more for Qwen2.5-1.5B, whose
  page is 64 positions, and 16,777,216 blocks or more for Qwen2.5-0.5B, whose page is 128.
- **`sslm_kv_pool_overhead_size`** is larger at a cap the page size does not divide, by
  `block_count · (ceil(cap / B) · B − cap)` positions of K/V. `sslm_kv_block_size` and the no-budget
  save are unchanged at every cap.
- **`sslm_prefix_freeze`**, on its first call, returns the prefix's unused pages to the pool. A pool
  can therefore admit more handles than in 1.11.0, never fewer: a pool of N blocks whose handles were
  all made by the 1.11.0 verbs still admits N handles.
- **`sslm_seq_reset`** no longer zero-fills the sequence's K/V memory. No read reaches the old rows,
  and a no-budget save still writes zeros past the live length, so saved blobs are unchanged.
- **Restore** refuses a blob of any format that is mid-token at the context cap, with
  `SSLM_INVALID_ARGUMENT`. No save produces such a blob.
- **Restore** reads `SSB6`. An `SSB6` blob must be passed with exactly the size its save returned;
  `SSB5` and older still accept a larger buffer.
- **`sslm_status`** gains `SSLM_KV_BUDGET_EXCEEDED`, appended as ordinal 29. Only budget-mode
  sequences and prefixes can return it. Every other ordinal is unchanged.

A host that adopts budget mode should know:

- An `SSB6` blob cannot be read by 1.11.0 or earlier, which refuse it on its magic.
- Once a budget-mode handle is in a pool, admission follows the pages actually held: a budget
  sequence that shares a released prefix's pages keeps them counted until it resets, adopts or
  releases. Size admissions from `sslm_kv_pool_stats`' `free_pages`.
- Restoring a cohort without its prefix handles holds each sequence's prefix span privately until it
  resets or re-adopts (the 1,405 pages above, against 505). Pass each restore its live prefix
  handle through `sslm_seq_restore_shared`.
- A budget sequence's adopt of a prefix from another pool is refused with `SSLM_INVALID_ARGUMENT`.

A host can test for the surface at compile time with `SSLM_HAS_PAGED_KV_ABI`.

## Not in this release

- **GPU paging.** GPU sequences keep one whole-cap buffer each, and the GPU has no prefix verbs. GPU
  paging is planned for 1.13.0.
- **Memory savings for the 1.11.0 verbs.** They keep one block's pages per handle, and a no-budget
  save is still the whole block.
- **A removed cap.** The context cap stays: RoPE tables and the attention scratch are sized by it.
  Paging only makes a high cap cheaper to reserve.
- **Automatic prefix matching, adapter-shaped prefixes, and batched shared-prefix attention.**
  Prefixes are explicit, base-only handles, and each sequence still reads shared pages in its own
  attention step.
